The problem

An LLM app can get worse without anything breaking.

The tests pass, the app answers, the demo works. Then a prompt edit, a model version or a library upgrade changes one answer your client depended on, and nothing in the pipeline says so.

How it usually goes

  • Re-run the evals and look at the average
  • No way to tell a real drop from the judge having a bad day
  • What was approved, and when, lives in someone’s notebook
  • The client finds the regression first

With an approved reference in the repo

  • Every change is compared case by case
  • The judge’s noise is measured before a drop is called
  • The reference is a file in a PR, with a commit and a name on it
  • CI stops before the release does

How it fits

It lives in your repo, not on a server.

Nothing to sign up for and nothing to host. The reference is a file, and the tool is a package.

The reference is a file in your repo

Scores, prompt and model config, committed next to the code. It changes through a PR, so there is a commit and a name on every approval.

Try it

The quickstart runs without an API key.

You need Python {{ home.requires_python }}. The model call in the guide is canned, so you can see the whole loop before wiring a real provider.

  1. digline run

    Runs the suite and writes a run file.

  2. digline promote

    A person approves that run as the reference.

  3. digline compare

    Every later run is checked against it.

Roadmap

  
Where it’s headed

  
Shipped — verdict credibility: a drop is a regression only when
  it leaves the interval the baseline measured across its own samples, and the
  open work now is adoption.

  
Two things will never be on the roadmap. A hosted service that
  receives your payloads — prompts, outputs and the judge stay in your
  perimeter. And usage data collection, ever.
